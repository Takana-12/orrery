## 1. 結論

**方式D（独立した薄いControl Room）を採用する。** 構成は次のとおり。

| 層 | 選定 | 主な理由 |
|---|---|---|
| Claude接続 | 公式 **Claude Agent SDK**（`canUseTool` コールバック） | AskUserQuestionと権限要求が `toolUseID` 付きの構造化データで届き、構造化して返せる【実機】 |
| Codex接続 | 公式 **Codex App Server**（stdio JSON-RPC、1プロセスで全スレッド） | 承認・構造化質問・受領確認通知（`serverRequest/resolved`）が揃っている【実機】 |
| Control Core | **Node.js / TypeScript のローカル常駐プロセス** | Claude Agent SDKがTypeScriptネイティブ。Codexは子プロセスなので言語を選ばない |
| Windowsプロセス管理 | **Job Object**（kernel32をFFIで直接呼ぶ） | 親が死んだ孫プロセスも捕捉・一括終了できる【実機】。ネイティブビルド不要 |
| UI | **React + TypeScript のSPA**、Coreとは型付きHTTP＋SSEで通信 | シェル（ブラウザ／Edgeアプリウィンドウ／Tauri／Electron）を後から差し替えられる |
| 永続化 | SQLite（追記型イベントログ＋投影） | ローカルファースト。再起動時に再構築できる |
| ACP | **主経路にしない。** 将来、他エージェント用の第3アダプターとして追加 | Claude/Codexでは同じ公式インターフェースの上に被さるラッパーで、情報が落ちる【コード】 |
| Orca | 採用しない。Phase 4の任意連携に格下げ | 公開プラグインAPIでは最重要要件が実現できない【コード】 |

一言でいうと：**質問と承認を構造化して往復できるかどうかは「エージェントの接続を自分で所有しているか」で決まる。** Orca・Nimbalyst・T3 Code・Paseo・vibe-kanbanのいずれも、構造化往復を実現している経路は同じ2つ（Claudeの`canUseTool`、Codexのapp-serverサーバーリクエスト）だった【コード】。その2つを直接使い、Inboxを中心に薄く組むのが最短で、かつ既存製品のUI構造に引きずられない。

### 2.4 Windowsプロセス管理【実機】

`node poc/05-winjob.mjs` の結果（`docs/evidence/winjob-result.json`）。

**後始末：** 子プロセスが「切り離した孫プロセス」を起動して先に終了するケースを作った。

- `taskkill /PID <親> /T /F` は「プロセスが見つからない」で失敗し、孫は生き残る（親PIDをたどる方式の限界）。
- Job Objectは孫を保持し続け（`activeProcesses: 1`）、`TerminateJobObject` で消えた。
- Claude Code・Codexともに、正常終了後にJob内の残存プロセスは0だった。

**メモリ実測（1回の計測、ワーキングセット合計／プライベートコミット合計）：**

| 対象 | プロセス数 | ワーキングセット | プライベート |
|---|---|---|---|
| Codex app-server、スレッドなしアイドル | 1 | 59 MB | 26 MB |
| Codex app-server、1スレッドが承認待ち | 8 | 259 MB | 129 MB |
| Claude Code、1セッションが承認待ち | 2 | 241 MB | 510 MB |

計測の定義：Job内の全生存プロセス（ルート＋子孫）の瞬間値の合計。ワーキングセットは共有ページを重複計上するので過大になる。プライベートはコミット量で、物理メモリ使用量ではない。1回だけの計測で、ばらつきは見ていない。

読み取れること：**Claude Codeは1セッション＝1プロセスで約240MB**。20セッションを常駐させると約5GBになる。「登録」と「常駐」を切り離す設計書§9の方針は実測でも妥当。Codexは1プロセスに全スレッドが載るので、スレッド追加の増分は別途計測が必要【未確認】。

## 3. 4方式の比較と不採用理由

詳細は[機能実現性の比較表](02-機能実現性マトリクス.md)。ここでは判断の根拠だけ。

### A. Orcaプラグイン — 不採用

調査対象：`stablyai/orca` HEAD `b4c51f9`（2026-11-22）、Host API 1.10【コード】。

- **質問内容を読めない。** 公開41メソッド・5イベントのどれも、質問文・選択肢・要求IDを運ばない。`agents.list` と `agent.status.changed` は `working | blocked | waiting | done` の状態だけ。会話本文は仕様として明示的に除外されている。
- **構造化して答えられない。** 入力経路は `terminal.sendText` だけで、しかも**現在フォーカス中のワークスペースの端末にしか送れない**。横断Inboxは端末文字列方式でも成立しない。
- 最も近い `agent.tool.before` フックは2秒の期限、結果は「拒否」か「入力の書き換え」だけ。**Windowsではフックが `{}` を即返す実装**で、判断を待たない。
- パネルは右サイドバーのみ、フレームはループバックを含めネットワーク不可。sidecarは `trusted-worker` から起動できるが、ワーカーは「いつでも停止されうる」。
- メモリ・プロセス情報はプラグインに一切公開されていない（issue #45375 は未回答のまま）。

設計書§4の採用条件「最重要要件を本体の無理な内部API依存なしに実現できる」を満たさない。

### B. Orcaフォーク — 不採用

- Orca内部には必要なものが揃っている【コード】。「Chat」セッションでは `agentSession.respondToApproval` / `respondToQuestion` / `subscribeStatus` があり、Job Objectとセッション単位のメモリ計測もある。
- ただしその構造化経路の正体は、Claude Agent SDKの `canUseTool` と `codex app-server` であり、**方式Dで直接使うものと同じ**。Orca固有の能力ではない。
- 端末（PTY）セッションはOrca自身も、AskUserQuestionへの回答をキー入力の模倣で行っている。Windowsではさらに弱い。
- コスト：`src/` に非テストTypeScript約310万行、直近3週のコミット数が週1,782〜2,607、Host APIは2週間で1.1→1.10。追従負担が大きく、横断Inbox画面は結局自作になる（既存のInbox UIは見つからなかった）。

### C. 既存OSSのフォーク — 不採用（一部を参考・流用）

| 候補 | ライセンス | 接続方式 | Inboxからその場で回答 | 判断 |
|---|---|---|---|---|
| Nimbalyst | MIT | Claude: Agent SDK／Codex: app-server | 不可（注意リストは該当セッションへ移動するだけ） | 参考・部分流用。約80万行のエディタ製品 |
| Emdash Classic | Apache-2.0 | 両方ACP経由 | 不可。AskUserQuestionは非対応（クライアントがelicitationを宣言していない） | 参考のみ |
| T3 Code | MIT | Claude: Agent SDK／Codex: app-server（7種のサーバーリクエスト対応） | 専用Inbox画面は見つからず | **次点**。Effect-TS全面採用、アダプター1ファイル1.5万行、クラウド機能付き |
| Paseo | Apache-2.0 | 同上 | 専用Inbox画面は未確認 | **次点**。プロバイダー中立の要求モデルが最もきれい。ただしIDE一式 |
| vibe-kanban | Apache-2.0 | Claude: CLI制御プロトコル／Codex: app-server | 「Needs Attention」はワークスペース一覧 | 参考。開発元は2026-04に解散しコミュニティ保守、承認はメモリ上のみ |
| Coral | Apache-2.0 | 対話CLIをPTYで実行＋フック | Inboxはあるが**端末への文字入力で回答** | UXと`winjob`実装の参考 |

すべて【コード】（一部はREADMEのみ）。共通する事実：

- **「横断Inboxからその場で要求IDに対して回答する」画面を持つものは見つからなかった。**
- 保留中の要求を再起動後も保持するものはない。Job Objectを使うのはOrcaとCoralだけで、Nimbalystはコード中のコメントで未対応を認めている。セッション単位のメモリ計測はOrcaとT3 Code以外にない。
- つまり、フォークしても最重要部分（Inbox、失効処理、プロセス所有）は自作になり、不要なエディタ・同期・モバイル機能を抱える。設計書の原則8「Lean」に反する。

**流用するもの（ライセンス表示を保持）：** T3 Codeの要求モデルにある `responseCapability: live | message | not_resumable` の考え方、Paseoの `getPendingPermissions()` / `respondToPermission()` というプロバイダー境界、Coralの「サスペンド状態で起動→Job割り当て→再開」パターン、Nimbalystの `docs/INTERACTIVE_PROMPTS.md`（CodexのID対応付けでの失敗例）。

### D. 独立アプリ — 採用

PoCで、両プロバイダーのアダプター中核部は合計約300行で成立した。設計書§4の採用条件「正式な接続手段で、質問/承認の往復・会話復元・Windows上のプロセス管理が確認できる」は、PoCとMVPのE2Eを合わせてすべて【実機】で満たした。

**引き受けるコスト（正直に）：**

- 会話の表示、ストリーミング、diff表示、再接続、MCPのelicitation、サブエージェント、プランモード承認などの「裾野」は自分で作る。T3 CodeやPaseoが数万行かけている部分。MVPでは必要最小限に絞る。
- 両社のインターフェース変更に自分で追従する。Codex app-serverはCLIのヘルプ上「experimental」表記【実機】。対策はアダプター層の分離とバージョン固定、スキーマ生成（`codex app-server generate-ts`）による型の差分検出。

## 4. ACPの位置づけ

調査対象：ACP v1（安定版、schema 1.34.1）、`claude-agent-acp` 0.109.1、`codex-acp` 2.9.0【コード】。

当初の想定より成熟していた。安定版v1に構造化質問（`elicitation/create`、2026年7月に安定化）があり、両アダプターがAskUserQuestionとCodexの`request_user_input`をそこへ対応付けている。それでも主経路にしない理由：

1. **両アダプターは、方式Dが直接使う公式インターフェースのラッパーである。** `claude-agent-acp` はClaude Agent SDKを、`codex-acp` は `codex app-server` を包んでいる。層が1つ増えるだけで到達できる機能は増えない。
2. **情報が落ちる。** Codexの `serverRequest/resolved`（受領確認）・`availableDecisions`・レート制限・アーカイブ、Claudeの拒否時メッセージ・権限ルールの提案・フックイベントが、落ちるか `_meta` 経由になる。設計書§12の「acknowledgementを保持する」に直接響く。
3. **罠がある。** クライアントが `elicitation.form` を宣言しないと、ClaudeはAskUserQuestionが無効化され、Codexは質問に空回答を返してエラーも出ない。
4. **変化が速い。** `claude-agent-acp` は0.x系で11月だけで16リリース。v2はプレビュー段階で権限要求の形が変わる。JetBrains AIR向け拡張が中心で、それ以外のクライアントは使用例が少ない経路になる。
5. 調査した上位3つのOSS（T3 Code、Paseo、vibe-kanban）は、いずれもClaude/Codexにはネイティブ接続を使い、ACPは他エージェント用に限っている。

**方針：** 内部に自前の `ProviderAdapter` インターフェースを持ち、Claude用・Codex用はネイティブ実装、将来Gemini等を足すときにACPアダプターを3つ目として追加する。ACPアダプターのAskUserQuestion対応コードは良い参考実装（Apache-2.0）。

## 5. 既存サブスクリプションとの互換性

### Codex（ChatGPTプラン）— 個人のローカル利用は公式文書上、容認

- 【実機】`codex app-server` はChatGPTログイン（Plus）でそのまま動いた。認証情報にはこちらから一切触れていない（公式バイナリが `~/.codex` を自分で読む）。
- 【文書】公式ドキュメントの認証の節は、app-server認証を使うローカル／オープンソースのアプリは継続利用できるとしつつ、「Sign in with ChatGPT」への移行を推奨している。同じ箇所に「app-server認証は商用・ホスト型サービスには一度も許可されていない」という趣旨の記述がある。
- 【実機】CLIのヘルプでは `app-server` は「[experimental]」表記。【文書】JSON-RPC面は後方互換を意図した設計とされ、stdioが唯一サポート対象のトランスポート。
- 結論：**個人用・ローカル専用である限り問題ない。** 他人に配布してログインさせる製品にする場合は別途確認が必要。

### Claude（Pro/Maxプラン）— 動くが、規約上の明文の許可はない

- 【実機】Agent SDK経由で、APIキーなし・Maxプランのログインで動いた。SDKは公式の未改変バイナリを起動するだけで、こちらは認証情報に触れていない。
- 【文書】2026-06-15に予定されていたAgent SDK利用枠の変更は**保留**され、Agent SDK・`claude -p`・サードパーティアプリの利用は引き続きサブスクリプションの枠を消費する（サポート記事「Use the Claude Agent SDK with your Claude plan」）。
- 【文書】Maxプランには月額$100のAPIクレジットが付くが、これは**Console APIキーで実行した場合にのみ**使われる。プランのログインで実行した分には使われない。
- 【文書】規約ページの記述：OAuth認証は「Claude Codeおよび他のネイティブAnthropicアプリの通常利用」を支えるためのもの。**製品・サービスを作る開発者**はAgent SDKを使う場合を含めAPIキー認証を使うべきで、サードパーティがClaude.aiログインを自社アプリに提供すること、認証情報やセッショントークンを収集・保存・仲介することは禁止。一方で、プランの利用上限の説明には「Claude CodeとAgent SDKの通常の個人利用を想定」とある。
- **はっきりしない点：** 「自分のPCで、自分のプランで、自作ツールからAgent SDKを使う」ことを明示的に許可する文も禁止する文も見つからなかった【文書】。記述の方向性（個人の通常利用を想定、禁止対象は他者への提供と資格情報の仲介）からは許容範囲と読めるが、**これは私の解釈であり保証ではない。** 規約ページは個別の用途については営業窓口へ問い合わせるよう案内している。

**このリスクへの設計上の備え：**

1. 認証情報を読まない・保存しない・中継しない。ログインはClaude Code自身の画面で行う（`~/.claude/.credentials.json` に触れない）。
2. 他人に「Claude.aiでログイン」させる配布物にしない。個人用に限る。
3. Claudeアダプターの認証を設定で切り替えられるようにする（プランのログイン／APIキー）。APIキーに切り替えればMaxの月$100クレジットが使える。
4. 方針が変わった場合の退避路として、**対話CLI＋フック方式**を第2のClaudeアダプターとして設計に含める。公式文書に、`PermissionRequest` フックで許可／拒否を返せること、`PreToolUse` フックでAskUserQuestionに `updatedInput.answers` で回答できること、フックをユーザー設定に置けば全セッションに効くこと、HTTPフックの既定タイムアウトが600秒であることが記載されている【文書】。**ただし対話セッションで回答が実際に通るかは未確認**で、文書の説明は `-p` を前提にしている。この方式は設計書の「Externalセッション」取り込みにも使える。
5. 確実性が必要なら、Anthropicに用途を問い合わせる（ユーザー側の判断）。

### 守ること（設計書§15と一致）

Claude/ChatGPTのWeb UIの自動操作、認証トークンの抽出・転用、Claude Codeバイナリの改変は行わない。

## 7. シェル（デスクトップアプリの外殻）の判断

**当面：Coreが `127.0.0.1` でUIを配信し、Edgeのアプリウィンドウ（`msedge --app=URL`）または通常のブラウザで開く。**

- 理由：このPCにはRustツールチェーンが無く【実機】、Tauriを選ぶと最初の作業がツール導入になる。ElectronはChromium一式を同梱して常駐メモリを増やすため（増分は未計測）、設計書の「Resource-aware」に逆行する。Edge（WebView2）は既にOSに入っている。
- UIとCoreを型付きHTTP＋SSEで分離しておけば、後でTauriやElectronで包むのは外殻の追加だけで済む（設計書§0-6「実行基盤にUIを密結合させない」）。
- 欠点：タスクトレイ常駐、OS起動時の自動起動、グローバルショートカットは別途用意が必要。通知はWeb Notifications APIで代替する。**ここはユーザーの好みで変えてよい判断**なので、Tauri/Electronを希望する場合は指示してほしい。

ローカルHTTPの安全策：`127.0.0.1` のみにバインド、Host/Originヘッダー検証（DNSリバインディング・CSRF対策、PoCで実装済み）、起動ごとのランダムトークン（MVPで追加）。

**設計上の注意：**

- 検証コマンドは作業を作った人間が入力したものを、シェルでそのまま実行する。10分でタイムアウトし、検証が残したプロセスは終了させる。

- コマンドを実行できるエージェントは、渡された環境変数を読める。伏せ字は記録と画面からの漏えいを防ぐもので、エージェントから隠すものではない。開発用／本番用の分離や、操作ごとの承認は未実装。
- Codexは、秘密らしい名前の変数を出力するコマンドの実行を自分で断ることがあった（実機で確認）。
- 作業名の生成はプランの利用枠を少量使う（1件ごとに短いhaikuの実行）。Claudeにログインしていない環境では仮の名前のままになる。
- 順番待ちはメモリ上にあり、Control Roomを再起動すると「中断」になる（指示文は会話の記録に残らないので、送り直しが必要）。

### 9.7 Windowsアプリ化（2026-11-23追記）

§7では「Edgeのアプリウィンドウ＋ローカル常駐プロセス」を当面の外殻としていたが、ユーザーの要望によりWindowsのアプリに変更した。

**選定：Electron。** Control Roomの中核がNode.js（Claude Agent SDKがTypeScript）なので同じプロセスで動かせ、追加のツール導入なしで作れる。Electron 45（Node 24同梱）でTypeScriptの直接実行・内蔵SQLite・FFIがそのまま動くことを確認したため、ビルド工程も増えていない【実機】。Tauriは常駐メモリが小さい見込みだが、RustとC++ビルドツールの導入が必要で、中核を別プロセスで抱える構成になるため見送った。UIと中核の境界（HTTP＋状態ストリーム）は変えていないので、外殻は今後も差し替えられる。

| 項目 | 内容 | 確認 |
|---|---|---|
| アプリの構成 | `apps/desktop/main.mjs`。中核を同じプロセスで起動し、専用ウィンドウにUIを表示。ページにはNodeの機能もブラウザの権限も与えない | 【実機】開発起動とパッケージ版の両方で、ウィンドウの生成とUIの接続を確認 |
| パッケージ | `npm run package` で `Control Room.exe` を生成（約740MB：Electronと、Claude Codeのバイナリを含むAgent SDK）。スタートメニューに登録 | 【実機】生成と登録。asar形式では同梱のClaude Codeバイナリを起動できなかったため、asarなしで作る |
| パッケージ版でのエージェント実行 | Claude（自動命名・承認依頼・プロセスのJob管理）、Codex（返答完了） | 【実機】 |
| トレイ常駐 | ウィンドウを閉じても動き続ける。トレイのアイコンと説明文に件数を表示 | コードのみ。**表示は目視していない** |
| 通知 | 新しい依頼が来たとき、ウィンドウが前面にない場合にWindowsの通知を出し、タスクバーを点滅させる | 【実機】通知の発行まで（ログで確認）。**画面に表示されたかは目視していない** |
| 終了 | トレイのメニューから。動いている作業があれば確認 | APIからの終了で、エージェントのプロセスが残らないことは【実機】。確認ダイアログは未検証 |
| 多重起動の防止、Windows起動時の開始 | Electronの標準機能を使用 | 未検証 |
| アプリ自体のメモリ | 4プロセス合計で約450MB（ワーキングセット合計、起動12秒後に1回計測） | 【実機】 |

**引き受けたコスト：** アプリ自体が約450MBを常時使う（Edgeのウィンドウ方式では、Control Room側はNodeの1プロセスだけだった）。配布物が約740MB。インストーラーと自動更新、コード署名はない。

**同時実行数の既定値を8件にした**（ユーザーが普段8件ほどを並行させるため。最大20件）。

### 9.8 名前の変更と追加機能（2026-11-23追記）

**名前を Orrery（オーラリー）に変更した。** オーラリーは太陽系儀、つまり軌道を回る天体の模型のこと。複数のエージェントが回り続けるのを中心から見守る、という題材に合わせた。アイコンも同じ発想で、傾いた軌道と小さな星にした（判断待ちがあると天体の1つが琥珀色になる）。データの保存先（`%LOCALAPPDATA%\AgentControlRoom`）と環境変数名は変えていないので、これまでのデータはそのまま使える。

| 機能 | 仕組み | 確認 |
|---|---|---|
| モデルと思考量 | 新しい作業の画面では1つのボタンにまとめ、押すとモデルが縦に並ぶシートが開く。思考量は段階つきのスライダー。既定は各エージェントの先頭のモデルと「中」。思考量はClaude Agent SDKの `effort`、Codexの `turn/start` の `effort` にそのまま渡す | 【実機】一覧に各モデルの思考量の段階が含まれること、指定した思考量で両エージェントの作業が動くこと、シートの表示 |
| 承認を任せる | 作業ごとに選ぶ。Claude Codeは `permissionMode`（`acceptEdits` / `auto`）、Codexは `approvalsReviewer: auto_review`。Orrery自身は承認の判断をしない。作業を再開するときも同じ設定を引き継ぐ | 【実機】両エージェントで、コマンドが要対応に届かずに実行された |
| この作業の間は常に許可（Claude） | Claude Codeが提案する許可ルールを、その作業の間だけ適用する | コードのみ。未検証 |
| 利用状況 | Codexは `account/rateLimits/read`（使用率とリセット時刻）。Claudeは実行中に届く利用枠の通知（使用率が含まれないことがあり、その場合は状態だけ表示）。トークン数は各ターンの報告値を記録して集計 | 【実機】Codexの使用率、Claudeの状態とリセット時刻、両方のトークン数 |
| ログイン状態の検知 | Claudeは同梱の公式バイナリの `auth status`、Codexは `account/read`。起動時と5分ごと、および認証らしいエラーが出たときに確認。認証情報のファイルは読まない | 【実機】ログイン中であることとプランの検知。**ログアウト状態の検知は未検証** |
| アプリからのログイン | Claudeは公式バイナリの `auth login`、Codexは `account/login/start` で公式のログインページを既定のブラウザで開き、完了を待つ。資格情報はアプリ内では扱わない（アプリ内の埋め込み画面にはしていない） | コードのみ。**未検証**（ユーザーをログアウトさせる必要があるため） |
| フォルダ選択 | エクスプローラーの標準の「フォルダーの選択」ダイアログ（Electronの標準機能） | コードのみ。**未検証**（人の操作が必要） |

二重起動の防止は、ユーザーが起動していた旧アプリがポートを使用中の状態でコンソール版を起動し、データに触れる前に終了することを確認した【実機】。

### 9.9 見回りを減らす工夫（2026-11-23追記）

| 工夫 | ねらい | 確認 |
|---|---|---|

### 9.10 文章からの読み取り、あなたの作業、コマンドのリンク、保存データ（2026-11-23追記）

| 機能 | 仕組み | 確認 |
|---|---|---|
| 答えた依頼はすぐ消える | 送信した時点で画面から外す。8秒たっても受領が確認できないものだけ、その旨を添えて再表示する。受領確認そのものの記録は変えていない | 画面に実装。**再表示は未検証**（受領が遅れる状況を作れていない） |
| 文章で尋ねられた質問を拾う | ターンが終わるたびに、最終返答を最小モデル（haiku、ツールなし）に読ませ、質問と選択肢を抜き出して依頼にする。答えは次のメッセージとして送る。作業の状態は変えない（エージェントは待っていないため）。作業が先に進んだら依頼は取り下げる | 【実機】R1・R2：Codexが文章で出したA案／B案が選択肢になり、選んだ答えが次のメッセージとして届いた |
| あなたの作業 | 同じ読み取りで、人間にしかできない残作業を手順として抜き出す。全部済ませると作業は完了（片付け） | 【実機】H1・H4 |
| コマンドのリンク | 会話中のコード片のうちコマンドらしいものをリンクにし、確認のうえ作業フォルダで実行。結果を表示・記録し、エージェントに返せる。エージェントが書いていないコマンドは拒否 | 【実機】H2・H3（実行・記録・手順の自動チェック・拒否）。画面でリンク表示を確認。**クリックからの確認ダイアログと結果表示は未検証** |
| 保存データの整理 | サイズと件数を表示。片付けた作業の会話記録と生データを削除して領域を返す。アプリのキャッシュも消す。出来事の記録は残す | 【実機】P1。アプリのキャッシュ削除は未検証 |

**知っておくこと：**

- 読み取りは別のモデル呼び出しなので、プランの利用枠を少し使う。質問や依頼らしい言い回しがない返答では呼ばない。読み取りが間違うこともある（質問でないものを質問として出す、手順を落とす）。元の返答は依頼の「生データ」と会話でいつでも確認できる。
- 読み取りにはClaudeを使うので、Claudeにログインしていない環境では働かない（Codexだけを使う場合も同じ）。
- 画面が重くならないよう、ページに送る依頼は「未処理のもの＋直近300件」に限った。会話は200件ずつ読み込む。
