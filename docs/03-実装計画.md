## 3. ドメインモデル

設計書§6の区別（Task ≠ Turn ≠ Session ≠ Process）をそのまま型にする。

| エンティティ | 主な属性 | MVPでの扱い |
|---|---|---|
| Project | id、名前、ルートパス | フォルダを選んで登録 |
| Task | id、projectId、題名、受け入れ条件（文章） | セッション開始時に1つ作る。完了判定はPhase 2 |
| AgentSession | id、taskId、provider、providerSessionId、cwd、model、lifecycle、resumability | 中心エンティティ |
| Turn | id、sessionId、providerTurnId、状態、開始・終了時刻 | 記録する |
| ProcessGroup | id、sessionId（またはプロバイダー共有）、世代番号、ルートPID、状態 | Job Objectと1対1 |
| AttentionItem | 下記 | Inboxの単位 |
| AuditEvent | 追記型ログの1行 | すべての変更の元 |

### AttentionItem

```ts
interface AttentionItem {
  id: string;                     // 内部ID
  sessionId: string;
  source: {
    provider: 'claude' | 'codex';
    providerSessionId: string;    // Claude session id / Codex thread id
    processGeneration: number;    // プロバイダープロセスの世代（CodexのIDはプロセス内でしか一意でない）
    requestId: string;            // Claude toolUseID / Codex JSON-RPC id
    turnId?: string;
  };
  type: 'user_question' | 'permission_approval' | 'error_requires_action' | 'completion_review';
  status: 'pending' | 'answering' | 'resolved' | 'expired';
  responseCapability: 'live' | 'not_resumable';   // プロセスが生きている間だけ回答可能か
  createdAt: number;
  summary: string;                // 1行の要旨
  questions?: Question[];         // 選択肢・複数選択・自由記述の可否
  approval?: ApprovalRequest;     // ツール・コマンド全文・cwd・理由・選べる決定
  rawPayloadRef: string;          // イベントログ上の生データへの参照
  risk: 'normal' | 'elevated' | 'unknown';
  response?: { answer: unknown; sentAt: number };
  acknowledgement?: { at: number; evidence: string };
  expiredReason?: string;
}
```

### 状態機械

```text
AttentionItem:   pending ──回答──▶ answering ──プロバイダーの受領確認──▶ resolved
                    │                  └─ 送信失敗 ─▶ pending
                    └─ 取り下げ／ターン終了／プロセス終了 ─▶ expired

Session.lifecycle:  queued → running ⇄ waiting_for_user → turn_finished → (Phase 2: verifying → done → archived)
                    いつでも → interrupted / error
ProcessGroup:       not_started / alive / stopping / stopped / crashed      （lifecycleと独立）
Session.resumability: resumable / unknown / unrecoverable                    （同上）
```

不変条件（テストで固定する）：

1. 回答をプロバイダーへ渡すのは `pending` の項目に対して1回だけ。
2. `resolved` にするのはプロバイダーの受領確認を受けたときだけ。ボタンを押しただけでは `answering`。
3. 項目のプロセス世代が現在の世代と違えば、必ず `expired`。
4. 同じ（世代, セッション, requestId）の再配達は新しい項目を作らない。
5. 証拠がない状態は `unknown`（「状況不明」）と表示し、推測で埋めない。

## 4. イベントと永続化

追記型のイベントログを唯一の真実とし、画面用の状態はそこからの投影にする（設計書§12）。

```sql
CREATE TABLE events (
  seq        INTEGER PRIMARY KEY AUTOINCREMENT,
  at         INTEGER NOT NULL,          -- epoch ms
  type       TEXT NOT NULL,             -- 'session.created' など
  session_id TEXT,
  item_id    TEXT,
  payload    TEXT NOT NULL              -- JSON。秘密値は書かない
);
CREATE TABLE raw_payloads (             -- プロバイダーからの生データ（詳細表示用）
  id TEXT PRIMARY KEY, at INTEGER NOT NULL, session_id TEXT, body TEXT NOT NULL
);
-- 以下は投影（イベントから再構築可能）
CREATE TABLE projects (...);  CREATE TABLE sessions (...);  CREATE TABLE attention_items (...);
```

イベント種別（MVP）：`project.added`、`session.created`、`session.process_started`、`session.process_exited`、`turn.started`、`turn.finished`、`attention.opened`、`attention.answer_sent`、`attention.acknowledged`、`attention.expired`、`session.interrupted`、`session.error`、`core.started`。

**起動時の再同期：** `core.started` を記録し、プロセス世代を1つ進める。前の世代で `pending` / `answering` だった項目はすべて `expired`（理由：「Control Room再起動のため回答不可。セッションを再開して再度指示が必要」）にし、`running` / `waiting_for_user` だったセッションは `interrupted` ＋ `resumable` にする。プロバイダー側の実状態（Claude: セッションファイルの有無、Codex: `thread/read`）と照合して `resumability` を確定する。「実行中」と誤表示しないことを優先する。

## 5. プロバイダーアダプターの境界

```ts
interface ProviderAdapter {
  readonly provider: 'claude' | 'codex';
  capabilities(): ProviderCapabilities;   // 構造化質問の可否、複数選択の可否などを正直に返す
  startSession(req: StartRequest): Promise<void>;
  sendMessage(sessionId: string, text: string): Promise<void>;
  resumeSession(req: ResumeRequest): Promise<void>;
  interrupt(sessionId: string): Promise<void>;
  stop(sessionId: string): Promise<void>;
  shutdown(): Promise<void>;
}
// アダプター → Core は、イベントの発行のみ：
//   sessionEvent / attentionOpened(reply関数つき) / attentionAcknowledged / attentionWithdrawn / transcriptDelta
```

- `reply` 関数は発生元の要求に束縛されたクロージャで、Coreの外には出さない。UIが送るのは内部の項目IDと回答だけ。
- `capabilities()` の差はUIに表示する（例：「Codexの通常モードでは構造化質問は未対応」）。設計書の原則4「差を隠さない」。
- Claudeアダプター：1セッション＝1 `query()`。入力は非同期ストリームで保持し、追加メッセージを流し込めるようにする。ユーザー設定・プロジェクト設定は既定どおり読ませる（独自注入しない）。
- Codexアダプター：app-serverは1プロセスを共有し、起動は単一化する（PoCで踏んだ二重起動を防ぐ）。型は `codex app-server generate-ts` の生成物を使い、Codex更新時に差分で壊れた箇所を検出する。

## 6. セキュリティ境界

| 境界 | 方針 |
|---|---|
| ローカルHTTP | `127.0.0.1` のみ。Host/Origin検証。起動ごとのランダムトークンをURLフラグメントで渡しヘッダーで検証。CORSは許可しない |
| エージェント由来の文字列 | すべて非信頼入力。UIではテキストとして描画（HTMLとして解釈しない）。Markdownを描画する場合はサニタイズ |
| 承認 | 項目単位でのみ発行。セッション横断の「すべて承認」は実装しない。`acceptForSession` 等の範囲の広い決定は、範囲を明示した別ボタンにする。LLMによる自動承認は入れない |
| 認証情報 | Control Roomは読まない・保存しない・中継しない。子プロセスへは親の環境変数から `CLAUDE*` / `ANTHROPIC*` を除いて渡す（Control Room自体が別のClaudeセッションから起動された場合の混入防止。APIキーを使う設定のときだけ明示的に渡す） |
| ログ | 生データはローカルDBのみ。アカウントのメールアドレス等が含まれるため、リポジトリにコミットしない（`.gitignore` 済み）。秘密値のマスキングはPhase 2のenv管理と合わせて実装 |
| プロセス | Control Roomが起動したものだけをJobに入れ、Job単位でのみ終了する。PID指定の強制終了は使わない |
| 拡張 | プラグイン機構は持たない（MVP）。MCPは各エージェントの既存設定に従い、Control Room側からは追加しない |

## 7. 段階計画

### Phase 1：日常使用可能なMVP（実装済み）

UIは当面、依存なし・ビルドなしのHTML＋ESモジュール（`packages/server/public/`。`js/logic/` がDOMに触れないロジック層、`js/ui/` が表示層）で、下記パッケージ構成の `apps/ui`（React）は未作成。

| 順 | 作業 | 完了の定義 |
|---|---|---|
| 1 | `core`：型・イベント・状態機械・AttentionEngine＋単体テスト | §3の不変条件5つがテストで固定されている |
| 2 | `server`：SQLiteイベントストア、投影、起動時再同期 | 強制終了→再起動で、過去履歴が戻り、未回答項目が失効として表示される（設計書§14-4） |
| 3 | `provider-codex` / `provider-claude`：PoCから移植し、追加メッセージ送信・再開・停止を実装 | PoCのE2E 15項目が新構成で通る。Codexの `thread/resume` を実機確認 |
| 4 | `host-windows`：セッション／プロバイダーごとのJob、定期サンプリング | セッション行にプロセス数とメモリが計測時刻つきで出る。終了時に残存0 |
| 5 | `ui`：Inbox（キーボード操作つき）、実行中、完了ダイジェスト、詳細ドロワー（会話・生データ・コマンド出力） | 設計書§11のメイン画面。未対応0件の表示。通知（重複抑制つき） |
| 6 | プロジェクト登録とセッション開始フォーム（フォルダ、プロバイダー、指示文） | 2プロジェクト×複数セッションを並列実行できる |
| 7 | 承認の拡充：ファイル変更の差分表示、MCP elicitation、プランモード承認、Codexの追加決定 | 各要求種別がカードで扱える。未対応の種別は「未対応」と表示して自動応答しない |
| 8 | Runbookと起動スクリプト（Edgeアプリウィンドウで開く） | 手順どおりに新規環境で起動できる |

### Phase 2：認知負荷の削減

Taskの受け入れ条件と検証コマンド、`turn_finished` / `agent_claimed_done` / `validation_passed` / `task_accepted` の分離、完了候補と論理アーカイブ、Decision Memory、関連質問のグループ化（権限要求は束ねない）、優先度付け、日次ダイジェスト、env管理GUI（OSの資格情報ストア）。

### Phase 3：計算資源の最適化

20セッション時の実測、メモリ予算と同時実行数の制御、キュー、ターン終了済みClaudeセッションのプロセス解放と再開（再開はPoCで確認済み）、サスペンド起動によるJob割り当ての競合解消、開発サーバーの扱い。

### Phase 4：マルチエージェントと連携

タスク分割、hand-off artifact、Worktree、クロスプロバイダーレビュー。Externalセッション（対話CLI＋フック方式）の取り込み、ACPアダプター、Tauri等のネイティブ外殻、Orca連携は任意。

## 8. テスト方針

| 層 | 内容 |
|---|---|
| 単体（`core`） | 状態機械と不変条件。プロバイダーなしで高速に回す |
| アダプター契約テスト | 録画したプロバイダーメッセージ（PoCのログから秘密情報を除いたもの）を再生し、発行イベントを検証。課金なしで回帰確認 |
| 実機E2E | `poc/04-e2e.mjs` を新構成向けに移植。本物のClaude／Codexを使うので手動実行（費用：PoCではClaude側1シナリオ約$0.004相当、haiku使用時） |
| 障害注入 | Core強制終了、プロバイダープロセスのkill、回答直前のターン中断、ネットワーク断 |
