# 公開と運用（管理者向け）

GitHub の公開リポジトリ `Takana-12/orrery` を、管理者がどう更新・管理するかの手順です。貢献する側の手順は [CONTRIBUTING.md](../CONTRIBUTING.md) にあります。

## 0. しくみ

```
開発用リポジトリ（非公開・履歴ごと手元だけ）      公開用クローン（../orrery）          GitHub
  feature ブランチ → master にマージ   ──npm run sync-public──▶  main に 1 コミット  ──push──▶  Takana-12/orrery
```

- 開発用リポジトリの履歴には、個人のメールアドレスや消した画像が残っているので、**GitHub に push したり、公開リポジトリとつないだりしない。**
- 公開側の `main` は、`npm run sync-public` が作るコミットだけで進む。各コミットには `Synced-From: <master のコミット>` が付く。
- スクリプトは、ホームフォルダ・ユーザー名・メールアドレスが入ったファイルがあると止まり、テストが落ちても止まり、push 前に中身が master と同じかを確かめる。画像だけは中身を検査できないので一覧を出す（目で見る）。

## 1. はじめて公開する（private → public）

一度 public にしたものは、あとで private に戻しても、その間に誰かが clone・fork したものは消せない。公開の前に次を確かめる。

### 1-1. 中身の確認

- [ ] 未マージの作業ブランチがない（`git branch --no-merged master`）
- [ ] `npm test` と `npm run typecheck` が通る
- [ ] `npm run sync-public` を（`--push` なしで）実行し、止まらないこと、差分の一覧に意図しないファイルがないことを見る
- [ ] 画像（`docs/evidence` など）を 1 枚ずつ開き、ユーザー名の入ったパス、ニックネーム、メールアドレス、プランの契約内容、会話の中身が写っていないか見る
- [ ] README の「注意事項」が今の挙動と合っている（認証情報を読まない、127.0.0.1 だけ、平文で保存 など）
- [ ] LICENSE の名前と年が正しい
- [ ] 公開リポジトリの過去のコミットにも、個人の情報が入っていない（`git -C ../orrery log -p` をざっと見る。公開すると過去のコミットも全部見える）
- [ ] 公開用クローンの `user.email` が `…@users.noreply.github.com` になっている（スクリプトも確かめる）
- [ ] GitHub の Settings → Emails で「Keep my email addresses private」と「Block command line pushes that expose my email」がオン

### 1-2. 反映して push

```powershell
git switch master
npm run sync-public            # まず push せずに中身を見る
git -C ../orrery show --stat   # 確認
git -C ../orrery push origin main
```

（確認を済ませていれば `npm run sync-public -- --push` で一度に行える）

### 1-3. public にする

GitHub → Settings → General → 一番下の Danger Zone →「Change repository visibility」→ Public。

### 1-4. public にした直後に設定すること

無料のプランでは、次の設定は public のリポジトリでしか使えないので、公開した後に行う。

| 場所 | 設定 | 目的 |
|---|---|---|
| Settings → Code security | Secret scanning と **Push protection** をオン | トークン等をうっかり push するのを止める |
| Settings → Code security | **Private vulnerability reporting** をオン | SECURITY.md に書いた「Report a vulnerability」を使えるようにする |
| Settings → Code security | Dependabot alerts / security updates（オン済み） | 依存の脆弱性を知らせる |
| Settings → Rules → Rulesets → New branch ruleset | 対象 `main`、**Restrict deletions** と **Block force pushes** をオン。Bypass list に自分（Repository admin）を入れる | `main` が消されたり、履歴を書き換えられたりするのを防ぐ |
| Settings → Actions → General | 「Fork pull request workflows from outside collaborators」を **Require approval for all external contributors** に | 他人の PR で CI（Windows と macOS のテスト）が勝手に動かないように。PR を見て問題なければ「Approve and run」を押す |
| Settings → General → Features | Wiki をオフ（使わないなら）。Discussions はお好みで | 誰でも編集できる Wiki を残さない |
| Settings → Collaborators | **誰も追加しない** | 書き込みは自分だけにする |

#### 「誰でも出せるが、書き込めるのは自分だけ」について

GitHub の public リポジトリは、初めからこの形になっている。

- **書き込み（push、マージ、Issue を閉じる、ラベル付け）**：オーナーと Collaborators だけ。Collaborators に誰も入れなければ自分だけ。
- **ほかの人ができること**：見る、clone、Fork、Issue を書く、Fork からプルリクエストを出す、コメントする。
- Ruleset で「Require a pull request before merging」は**付けない**。付けると `sync-public` の直接 push が止まる（付けたい場合は自分を Bypass に入れる）。
- 荒らしが来たら：Settings → Moderation options → **Interaction limits** で、一定期間 Issue や PR を「既存の貢献者だけ」などに絞れる。個別の相手はプロフィールから Block できる。

### 1-5. 最初のリリースを作る

利用者は「Watch → Custom → Releases」で新しい版を知るので、版ごとに Release を作る。

```powershell
gh release create v0.4.0 -R Takana-12/orrery --target main --title "v0.4.0" --notes "最初の公開版"
```

## 2. ふだんの更新

1. 開発用リポジトリで、作業ごとにブランチを切って作業し、master にマージする
2. 版を上げる場合は `package.json` の `version` を上げてマージする。画面が変わったときは `npm run screenshots` で README の画像（`docs/images/`）も撮り直す（架空のデータで撮るので、個人の情報は写らない）
3. `npm run sync-public -- --push`（止まったら、表示された理由を直してからやり直す）。push すると GitHub Actions（`.github/workflows/ci.yml`）が Windows と macOS でテストとアプリの起動確認を行うので、`gh run watch -R Takana-12/orrery` などで両方が緑になるのを見る。**`main` に push した時点で利用者のアプリに更新が知らされる**（4 章）ので、OS に関わる変更は、先に下の「2-1」の方法で確かめてから `main` に出す
4. 版を上げた場合は Release を作る：`gh release create v<版> -R Takana-12/orrery --target main --generate-notes`（または `--notes` で変更点を書く）

### 2-1. `main` に出す前に、両方の OS で確かめる

手元にない OS（ふだんは macOS）で動くかは CI でしか分からない。`main` に出す前に確かめたいときは、公開用クローンで作ったコミットを**別のブランチ**に push して CI を走らせる。

```powershell
npm run sync-public                              # push せず、公開用クローンの main にコミットだけ作る
git -C ../orrery push origin main:refs/heads/ci/check   # そのコミットを ci/check ブランチとして push（CI が走る）
gh run watch -R Takana-12/orrery                 # Windows と macOS の結果を待つ
```

- 緑なら：`git -C ../orrery push origin main` で同じコミットを `main` に出し、`git -C ../orrery push origin --delete ci/check` で片付ける。
- 赤なら：`git -C ../orrery reset --hard origin/main` で公開用クローンを戻し、開発側で直して master にマージしてから、もう一度（`ci/check` への push は `--force` を付ける。`main` には決して force push しない）。

公開用のコミットは履歴を持たない 1 コミットなので、ブランチに出しても開発側の履歴は外に出ない。

`--message "<件名>"` でコミットの件名を変えられる（既定は「v<版> の更新を反映」）。取り込んだプルリクエストがあるときは、件名か Release の説明に `#番号` を書く。

## 3. プルリクエストが来たとき

GitHub 上では**マージしない**（次の `sync-public` で消えてしまう。スクリプトも、GitHub 上で作られたコミットがあると止まる）。

```powershell
git switch master
git switch -c pr/<番号>-<短い名前>
gh pr diff <番号> -R Takana-12/orrery | git apply
npm test
git commit -am "<内容>（Takana-12/orrery#<番号>、<相手の GitHub 名> さんより）"
git switch master
git merge pr/<番号>-<短い名前>
npm run sync-public -- --push
gh pr close <番号> -R Takana-12/orrery --comment "取り込みました。<反映したコミットの URL>"
```

相手を共同作者として残したい場合は、コミットメッセージの最後に `Co-authored-by: <名前> <ID+名前@users.noreply.github.com>` を付ける（ただし公開側は 1 コミットにまとまるので、公開側のコミットには付かない。必要なら `--message` で件名に書く）。

取り込まない場合は、理由を書いて閉じる。

## 4. 利用者のアップデートの流れ

利用者側の手順は README の「アップデート」に書いてある。

1. Orrery が起動時と 1 時間ごとに `git fetch` し、clone 元（origin/main）に新しいコミットがあれば、左バーの更新ボタンに点を付ける（`apps/desktop/remote-version.mjs`）
2. 利用者が更新ボタンを押すと、`git pull --ff-only` →（package.json / package-lock.json が変わっていれば）`npm install` → 作り直し → 再起動
3. 利用者が自分のコミットを積んでいる場合は、勝手にマージせず「手で git pull して」と表示する

つまり `main` に push した時点で、アプリを開いている利用者には 1 時間以内に知らせが出る。Release は、アプリを起動していない人やメールで知りたい人のため（Watch → Releases）に作る。

開発用リポジトリ（upstream のないブランチ）では確認しないので、管理者自身のアプリには何も出ない。

公開側の `main` は常に前のコミットに 1 つ積むだけ（履歴を書き換えない）なので、利用者の `git pull` は衝突しない（利用者が自分でファイルを変えていない限り）。**公開側で force push をしない**こと。利用者の `git pull` が壊れる。

## 5. もし個人の情報を公開してしまったら

1. すぐに Settings で private に戻す
2. トークンやパスワードなら、まず**無効にして作り直す**（履歴から消しても、見られた可能性は消えない）
3. 公開用クローンで、そのファイルを直したコミットを作る。過去のコミットにも残っているなら、公開リポジトリを作り直す（中身を 1 コミットにした新しいリポジトリにする）。そのときは利用者に「clone し直してください」と知らせる
4. GitHub のキャッシュに残った場合は、GitHub Support に削除を依頼できる
